Three findings

Each one measured before it was written down, per the house rule.

Measured REALISM.md 40 KB gate · js/renderer.js · js/app.js

The size gate counts bytes that are never transferred, while tap latency runs to 315 ms unwatched

68% of buildable doors blow the repo's own 40 KB gate — mean 55.3 KB, worst 282.9 KB. That number has been treated as a debt to pay down. It is measuring the wrong quantity. The SVG is never sent over a network: it is built in memory and assigned to innerHTML. Compressed, the worst door is 17.7 KB brotli. Bytes are not the cost.

The cost is DOM. The worst door is 2,130 nodes torn down and rebuilt on every single tap. So I measured what a customer actually feels, at 6× CPU throttle — the mid-tier Android someone is holding in their living room:

Under 100 ms reads as instant. 315 ms is a visible stutter on the interaction the customer performs most — and it is invisible on the desktop the site is developed on, where the same door repaints in 39 ms. Note also that coordinate precision is already tight (12,940 decimal numbers, 37 with more than two places, 0.0% recoverable), so bytes cannot be squeezed further anyway. Node count is the only lever.

Retire the byte gate. Replace it with a tap-latency gate on a throttled CPU — the one number that describes what a customer experiences.

Absent js/share.js · index.html

The product is WhatsApp-first and sends no picture of the door

message() is excellent — it is the most carefully reasoned file in the repo, and the recent work on it shows. But what Peretz receives is nine lines of text and a URL. He has to tap the link to see the door. His fabricator gets nothing he can forward.

navigator.share appears nowhere in the codebase, and there is no canvas path. On a phone — which is where every one of these orders is placed — Web Share Level 2 can attach a rendered PNG of the door directly into the WhatsApp message. The drawing is already a pure, self-contained SVG with no external references, so it rasterises cleanly.

Separately: index.html carries no og: or twitter: tags, no manifest, no apple-touch-icon. When a customer pastes their door link into WhatsApp it renders as a bare URL. And even with those tags the preview would show the default door, because the page is client-rendered from the query string and WhatsApp's crawler runs no JavaScript.

Blocked ASK-PERETZ.md · js/catalog.js

The thing stopping launch is not code, and it is being asked for in a format its reader will never open

PLACEHOLDER = true. Every price on screen is invented. ASK-PERETZ.md is 27 KB of Hebrew questions with a closing table of nine items, of which two — the ימין/שמאל handing convention and the prices per size — stop launch on their own.

The engineering has been ready for a while. What is missing is answers from one person who is not going to read a markdown file in a git repository. That is a solvable problem, and idea 3 below solves it with the site's own mechanism.

Ideas, ranked

Ranked by value delivered per unit of work, which is why the biggest technical change is not first.

01

Start from a door Peretz actually built

high valuelow effort

A customer arrives at a default door and roughly sixty options with no reference point. They have opinions about doors they have seen, not about quatrefoil versus vine.

Open instead on a grid of Peretz's real installed doors. Tap one and the configurator loads that door as the starting state, ready to change. "Like this, but black, and wider."

Why this is cheap The data pipeline already exists and already runs. tools/corpus.mjs derives a full buildable state for all 30 measured doors from their own records, and writes screenshots/corpus-links.md — a committed table of 30 real doors as query strings, each with the photograph beside it. The test suite already asserts every one of them is buildable. This is a gallery page over data that is sitting in the repo today.
02

Put the door inside the WhatsApp message

high valuelow effort

Rasterise the drawing to a PNG and attach it via navigator.share({ files, text }). Peretz opens WhatsApp and sees the door, with the spec and the DM- code underneath it. He can forward the picture to his workshop without the recipient needing the site at all.

Falls back to today's wa.me text link wherever Web Share Level 2 is unavailable, which keeps desktop and file:// working exactly as they do now.

One constraint, already documented here Canvas toDataURL throws SecurityError over file:// — REDESIGN.md found this during the raster-renderer evaluation. So the image path is https-only, which is the same condition shareUrl() already tests for. The two can share one guard.
03

Ask Peretz with the product itself

unblocks launchlow effort

Turn ASK-PERETZ.md into a single page he opens on his phone: each question as tappable options, pre-filled with what the catalogue currently assumes, prices as number fields. He works through it in ten minutes on a sofa.

At the end it produces a WhatsApp message back to you — the same mechanism the customer uses, pointed the other way. The answers arrive as text you paste into catalog.js.

Why this is the highest-leverage page in the project Nine questions stand between the current build and PLACEHOLDER = false. Every one of them is a five-second answer from the one person who knows. The format is the entire obstacle.
04

A workshop sheet at the other end of the code

medium valuelow effort

The DM- code decodes with no server — that is the whole point of it. So give it a destination: index.html?code=DM-…&sheet=1 renders a printable A4 spec sheet. Door elevation, dimensioned; the option list; the colour with its manufacturer reference; the handing stated in words and drawn.

Peretz stops retyping WhatsApp messages into whatever he currently orders from. The order becomes a document.

Reuses what exists decodeCode, specRows(state) and render(state) are all already pure and already exported. This is a stylesheet and a print layout over three functions that are finished.
05

Repaint only what changed

fixes finding 1medium effort

A colour tap is the most common interaction on the page and currently rebuilds all 2,130 nodes. It does not need to rebuild any of them — the paint flows through gradient stops and CSS custom properties. Hoist the palette to variables on the SVG root and a colour change becomes a handful of attribute writes.

That alone takes the commonest tap from 315 ms to near-zero on the worst door. Structural changes — window, grille, size — still rebuild, and should: they are rarer and the customer expects them to be a bigger event.

Guard it the way this repo guards things render(state) must stay pure and stay the source of truth. The assertion is that the incrementally-updated DOM is byte-identical to a full render() of the same state — otherwise this becomes exactly the two-computations-of-one-quantity defect CLAUDE.md §5 is about.
06

Give every shared link a real preview

high valueneeds infrastructure

The genuinely big change, and the only one that breaks the buildless, static, opens-from-a-folder constraint — so it is a deliberate decision, not a refactor.

A single edge function decodes the query string, renders the door server-side into a PNG, and serves og:image plus a real title. Every door link pasted anywhere — WhatsApp, SMS, Instagram DM — becomes a card with the customer's actual door in it. For a product whose distribution channel is people forwarding links, this is the difference between a URL and an advertisement.

What it costs, stated plainly The static site stays exactly as it is and keeps working from a folder; the function is additive and only ever serves crawlers. But it is a second runtime to keep in sync with the renderer, and REDESIGN.md's judgement on the 3D experiment — that a permanent second renderer was disqualifying — applies here and should be argued about before anyone builds it. Idea 02 delivers most of the same value with none of this.

What I would do first

In order, and none of these is a week's work.

01 Build the Peretz form. Nothing else ships until those nine answers exist, and it is an afternoon.
02 Ship the gallery entry point from corpus-links.md. Biggest change to what the customer experiences, smallest change to the codebase.
03 Attach the PNG to the message. The product is the handoff, and the handoff has no picture in it.
04 Add npm run latency and delete the 40 KB gate from REALISM.md, so the number the project watches is the one the customer feels.

One last note, in the spirit of the file that governs this repo: the reason all three findings survived a suite of 5.67 million assertions is the same reason CLAUDE.md keeps recording — every instrument here measures the drawing, and the product is the handoff. The byte gate watches the SVG. The audit watches the page. Nothing watches the message arriving on Peretz's phone, or the customer waiting 315 ms for a colour, or the nine unanswered questions that make every price on screen fictional.
